# 進度回報（staging）

僅部署 `v1.3.0-test` 到 Railway `XLeRobot-Staging / staging / XLeRobot-Test`。
主分支與正式環境不在此次變更範圍。新表皆以 `progress_` 開頭；沿用 `TASK_DB`、既有 S3 憑證及 `DISCORD_WEBHOOK_URL`，不需新增付費資源或套件。

## 行為

- 導覽順序：總覽 → 進度回報 → 分工&時程。
- 回報人、主題必填，內容可自由輸入。名稱上限 80 字、主題 200 字、內容 10,000 字。
- 每筆最多 20 個附件，總量 50 × 1024 × 1024 bytes；包含程式原始碼、常見壓縮檔、圖片、影片與 Office/PDF 文件。允許的副檔名列於 `progress.py` 的 `EXT`；不接受執行檔。
- 伺服器產生帶 `+08:00` 的時間；原始姓名、主題、內容、附件清單與版本關聯沒有修改／刪除 API。
- 可以接續任一有效回報。沿用原主題，記錄 parent/root 關聯，該主題版本號依序遞增，附件不複製。
- 姓名、主題、內文及附件檔名可搜尋，姓名／有效或作廢狀態可篩選。預設日期遞減。依主題檢視包含符合條件主題的完整歷程，依時間檢視只顯示符合條件的回報。
- 管理員沿用伺服器 `is_admin()` 與既有 SHA-256 key 驗證，不能由瀏覽器指定角色。必填作廢原因，作廢後才能另填原因永久移除附件；保留名稱、大小、理由、時間及操作紀錄。
- 四類事件：新增、接續、作廢、附件移除。獨立 SQLite outbox 每 5 秒檢查，失敗退避重試（最長 5 分鐘），重啟後補送，不受舊分工通知摘要設定影響。Discord 禁用所有 mention。
- 管理員可讀 `/api/progress/notification-status` 與 `/api/progress/{id}/audit`；介面顯示通知待送／重試數。

## 上傳與儲存

限制 request 長度、表單欄位／檔案數量、總大小、副檔名、檔名長度與控制字元；不採信上傳 MIME。隨機物件名稱使用 `progress/staging/` 前綴；本機測試使用獨立暫存目錄。原檔名只存資料庫；HTML 文字經過跳脫。
檔案經 API 強制下載，使用 `application/octet-stream`、`nosniff`、CSP sandbox。伺服器靜態檔案改採公開素材清單，封鎖原始碼、SQLite、Git 等檔案。
儲存失敗回滾整筆回報並嘗試清理物件；附件移除先停用公開下載、保存紀錄，再清理實體檔案，失敗由背景工作重試。

## 驗證

`python -m unittest -v test_progress`：使用工作區內暫存 SQLite 與本機 HTTP，不連正式／測試站資源。
包含完整生命週期、有效版本分支接續、權限／不可修改／搜尋篩選、50MB 邊界及超過 1 byte、儲存失敗回滾、靜態私密檔案封鎖、Discord 失敗重試、重啟補送與 mention 抑制。
`node --check progress.js` 檢查前端語法。

## 限制

- 既有管理員使用共用金鑰，紀錄可證明「已驗證管理員」，無法識別是哪一位自然人。回報姓名由填寫者自行聲明。
- 不包含病毒掃描、影片轉檔或線上執行／預覽；附件下載後需以可信工具開啟。
- SQLite 與 S3 不具跨服務原子交易；上傳期間程序突然終止，可能留下未關聯物件，需要按紀錄人工盤點。通知為至少一次傳遞，極少數回覆遺失可能重複通知。
- 清單目前一次載入符合主題的歷程，適合現有專題規模；大量紀錄時需分頁。兩個上傳並行上限，SQLite 寫入序列化，大檔上傳期間其他寫入可能等待。
- 實體附件移除無法復原；管理員介面另有確認。驗證部署時不操作既有附件刪除。
